# Harness 生命周期

一个 Runtime 进程从启动、跑完每一轮到退出，各个节点做什么、为什么这样做。状态本身怎么存、怎么恢复，见
[harness_state.md](harness_state.md)。

## 启动

- **先接上 Git 远端，再接受 run**：任何一轮动文件之前，工作区要先对齐到远端分支。
- **接不上也要起来**：远端挂了，或者工作区和远端都有内容时，失败记下来而不是退出进程。起不来的 Runtime 没法告诉用户出了
  什么问题，也没法让用户在修复期间接着干活。失败在 `/health` 上看得到，并且会挡住下一轮。
- **接上上一代的尾巴**：重新打开已有的状态目录或工作区时，后台任务主动补推上一代没推完的内容，不等下一轮来触发。
- **空 Runtime 由控制面放回会话**，见[恢复](harness_state.md#恢复先文件后上下文)。

## 一轮 run 的收尾

一轮 run 是 Runtime 自己的后台任务，不随连接结束。流结束后按这个顺序收尾，这段就是「屏障」：

1. 本地 commit 这一轮的文件。
2. 等控制面追平会话状态。
3. 放开 run 占位，`/health` 的 `running` 变回 false。

- **屏障里只做本地 commit**：纯本地、快、确定性强。commit 跑在工作线程上，线程不可取消，所以收尾发生在已被取消的任务里时
  它也能落地，并且提交的登记不会和 commit 本身断开。
- **push 不进屏障，由后台任务带重试去做**：关停时一轮的收尾时间有限，到点会被直接取消，一次网络往返在这个位置没法保证
  做完；平时它还会把一轮对话挂在网络上，用户看到的就是「卡住了」。
- **流结束只代表代码已在本地提交，不代表已经存到远端**。这是两个状态，`/health` 分开报，没配仓库和「已保存」也能区分开。
  字段含义见 `git/saver.py` 的 `SaveStatus`。
- **等控制面的这一步是屏障，但不是保证**：超时不会让这一轮失败，也必须放开占位，数据还在本地，后台任务会继续重试。
  正常跑完并追平的 Runtime 才是可以丢弃的，判断方法见[远程持久化](harness_state.md#远程持久化)。
- **一轮无论成败都 commit**：被停下或被取消时写了一半的文件也值得留着，但提交会标明是中断的，读历史的人不会把它当成
  跑完的一轮。这一轮没改文件时不留空提交。

## 退出前的行为

Runtime 随时可能被回收，而进程一走，workspace 盘和状态目录一起没了。所以「还没存好」时的两种离开都要有界：开始下一轮之前
等一等，进程退出之前再送一次。两者都是等得起就等，等不起就明确说出来，不无限挂着。

### 未保存时的下一轮：有界等待与逃生口

第一版只允许一份改动在途：上一轮还没存好时，让第二轮去改文件，「这个检查点里到底有什么」就成了难题。所以 `POST /runs`
会先等上一轮落地，等满上限仍未落地返回 409，`detail.code` 是 `workspace_save_pending`，和「已有运行中 run」的 409 靠
`code` 区分。重试也过不去的失败不必等，直接拒。

**必须有逃生口**：网络断了 push 可能永远落不了地，无限等待等于把用户锁在自己的会话外面。客户端可以带上
`POST /runs?allow_unsaved=true` 显式选择继续，这一轮的改动叠在未保存的改动上。这是要让用户明确做的选择，不是替用户做的
选择。继续之后 `/health` 依然报未保存：继续不等于假装已经存好了。

### 关停

普通路径从不在屏障里等 push。关停是唯一的例外：这时已经没有「以后」了，只存在本地的 commit 就等于用户丢了一轮。

收到 SIGTERM 后按顺序：

1. 拒绝新的 run（返回 503）。
2. 停下进行中的一轮。先按「停止」收尾，上下文还能提交；到点直接取消，文件照样提交，只是这一轮的上下文不再提交。
3. 取消后再等一小段，让它做完本地 commit。还没做完就不等了：commit 自己能走完，而这时它多半排在一个卡住的 push 后面，
   接着往下才送得出不需要 Git 锁的状态回写。
4. 在一个有界窗口里，把未推送的 commit 和未回写的状态送出去。
5. 停掉用户应用的子进程。

- **这一步不等控制面追平**：第 2、3 步的收尾跳过屏障里的等待，否则它会用掉第 4 步的预算。
- **push 和状态回写共用一个窗口，先 push**：push 通常只有几 KB，上下文可能好几 MB，先花在便宜的一半上，两半都送到的可能性最大。
- **窗口必须有界**：控制面给的宽限一到就 SIGKILL，超出预算的 drain 会被杀在半路，什么都没送出去。落后地退出好过这样，
  日志会说清楚哪些没送到。到点放弃的 push 可能仍会落到远端，这无害：下一个 Runtime 以 Git 为准，不信这一代的记录。
- **这几段加起来必须小于控制面的宽限**：具体秒数和合计只写在 `settings.py` 里 `SHUTDOWN_DRAIN_TIMEOUT_SECONDS` 的注释中，
  改任何一段都要回头核对。

### 空闲退出

空闲时间从进程启动起算，每轮 run 结束后重置，从未收到 run 也会到期。`GET /health` 不续命，否则轮询会让它永远不退出。
有 run 在跑时不会到期。

到期后给自己发 SIGTERM，走上面同一条关停路径，而不是直接 `os._exit`：直接退出会跳过 commit 推送和状态回写的最后机会，
丢掉的正是这个超时不想再为之付费的工作。关停路径以后新增的步骤也自动覆盖到这里。

同时起一个看门狗，到点无条件硬退（先停掉应用子进程），保证无论关停卡成什么样，空闲的 Runtime 都不再花钱。
