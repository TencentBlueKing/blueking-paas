# Harness 状态

Runtime 是可丢弃的，会话和代码不是。本文说明 Runtime 持有哪些状态、怎么存到沙箱之外、怎么恢复回来。
这些状态在一轮 run 和进程退出时怎么收尾，见 [harness_lifecycle.md](harness_lifecycle.md)。

状态分两块，归属不同：**上下文属于会话**，由控制面按会话保存；**文件属于 Project**，存在 Project 的 Git 仓库里，
可以被多个会话接着开发。后面很多决策都从这条区分来。

## 会话状态

按「怎么变」分成三份，都放在状态目录：

- **原始对话记录** `log.jsonl`：append-only，`seq` 连续递增。
- **AG-UI 事件历史** `ui_events.jsonl`：append-only，`seq` 连续递增。
- **会话上下文** `context.json`：发给模型的可信历史，可变文档，原子整体替换，带 `context_version`。

文件名不是配置项，它们是控制面读状态目录的契约，改名等于一次迁移。`cursors.json` 记录每份的编号起点和复制进度，
是这三份的元数据，不是第四份状态。

- **原始记录必须在消息产生的瞬间抄走**：压缩发生在一轮 run 的中间（每次模型请求之前）并写回历史，连这一轮刚产生的
  工具结果都可能被清掉，等 run 结束再导出就丢内容了。
- **`context_version` 不等于轮次**：一轮里压缩触发几次就提交几次，控制面不要假设两者同步。它只保证每次提交都向前走。
- **上下文不能从日志重建**：摘要是一次不可重放的真实 LLM 调用，冷启动重建上下文的唯一来源是 `context.json`，
  绝不能从 `log.jsonl` 拼出来。
- **bkaidev 对话中间层只读不写**：发给网关的历史只取自 `context.json`，不改写它，也不往原始记录写 OpenAI 原始报文。

## 远程持久化

配了控制面地址之后，三份文件不再是唯一副本，状态目录退化成一个可以丢弃的本地缓冲。没配时 Runtime 完全独立，状态只在
状态目录里。配置项见 [ref_settings.md](ref_settings.md#状态回写复制到控制面)。

- **本地文件就是 outbox**：追加本来就是整行落盘、`seq` 连续、半截尾巴加载时截掉，只差一份「推到哪了」的记录，
  不值得再建一个队列。一轮 run 不等网络，本地提交后由后台任务追上。
- **重发是安全的**：控制面按 `seq` 识别记录，确认丢失后再发一遍会被忽略。
- **日志先于上下文推送**：日志的滞后用户看得见，上下文只对冷启动有用，而冷启动时这个 Runtime 已经不在了。
  上下文只传最新版：一轮压缩两次只有最后一版值得传，而它可能有好几 MB。
- **「追平」看的是控制面真正持有什么**：判断依据是比较游标，不是这次推送有没有报错，因为推送中途落下的新记录很常见。
  发现缺口时继续补齐并重新触发后台任务。
- **能不能回收 Runtime 看 `/health`**：看 `replication_pending` 和 `pushed_*`，不要只看一轮结束了没有。

已知缺口：`run_id` 的重放检测只查本地日志，旧 Runtime 用过的 `run_id` 在空状态目录里查不到，所以控制面每轮都要生成新的 UUID。

## Git 持久化

状态目录之外，workspace 里的源码存进 Project 的私有 Git 仓库。没配仓库时 workspace 只在本地磁盘上。
配置项见 [ref_settings.md](ref_settings.md#workspace-工作区持久化基于-git)。

### 凭据只在一个进程的环境里

token 经环境变量交给 git，**不进命令行**。常见写法 `git -c http.extraHeader=...` 会把凭据放进 `argv`，而同一个容器、
同一个用户下的任何进程都能从 `/proc` 读到它，包括模型在 Shell 里跑的每一条命令，[安全](security.md#一密钥不进模型能用的环境)
里的第一层会被一个 `ps` 抵消掉。

配套的三条：

- header 按 URL 限定，重定向到别处不会带上。
- `.git/config` 里只有不含凭据的 remote URL。
- 系统与用户级 git 配置、继承来的 credential helper 全部关掉：helper 有权把凭据写到磁盘上，那正好是上面这些选择要避免的。

### 文件策略

- **保留**：源码、配置、静态资源、锁文件，**包含隐藏文件**（`.env`、`.python-version` 一类）。仓库是每个 Project 私有的，
  恢复时悄悄丢掉应用配置比存下来更糟。
- **默认忽略**：语言相关的构建产物与依赖目录，丢了只是重装一次，留着要吃掉全部延迟和体积预算。规则来自 vendored 的
  [github/gitignore](https://github.com/github/gitignore) 模板，写在 `.git/info/exclude` 里而不是写一份 `.gitignore`：
  `.gitignore` 属于用户项目，导入的项目可能已经有一份。更新模板用 `make update-gitignore-assets`。
- **二进制**原样提交；**符号链接**按链接本身提交，恢复时重建的也是链接。
- **体积上限是拒绝，不是告警**：超限时提交明确失败并报出是哪些路径，而不是悄悄把几百 MB 推上去。
  检查发生在暂存之前，失败不会留下半个暂存区。

### 不变量

- **一个远端、一条分支**。
- **永不强推**。远端有本地没有的提交时，推送失败并交给上层。仓库 token 长期有效，拦住一个跟丢的旧 Runtime 的唯一防线
  就是服务端拒绝非快进推送，留一个 force 开关等于给这道防线开后门。
- **工作区有文件、远端也有历史时拒绝合并**。覆盖工作区会丢未推送的工作，在远端 tip 上提交则会把远端有、本地没有的文件
  记成删除，两种做法都丢数据，所以这个选择留给调用方。

## 检查点：commit 必须配一个 tag

push 成功之后，这一轮的提交被钉上一个**不可移动的远端 tag**，然后才上报给控制面。

- **不能只存 SHA**：分支保护挡的是强推，挡不住「这个提交曾经存在、后来被回收了」。没有任何 ref 指向的提交是可回收对象，
  等到真要恢复时，检查点指向的可能已经什么都不是了。tag 就是让它保持可达的那个 ref，一个检查点一个。
- **先 push 后打 tag**：远端没有的提交，tag 只会指向空。
- **「已保存」的含义是可恢复，不只是已落盘**：检查点上报成功之前，这一轮仍然算没存好，下一轮也仍被挡着。
- **上报失败时重试同一个检查点**，绝不重新 commit：代码已经在远端了，再提交只会多出一个内容相同的 SHA。
- **记录的 `context_version` 取自做 commit 的那一刻**，不是 push 落地的那一刻：push 回来时会话可能已经是下一轮了。
  它只说明「这些文件是哪一轮写的」，控制面恢复时不拿它配对上下文。
- **一次 push 只产出一个检查点**：一次带上多个提交时（比如选择了带着未保存的改动继续），恢复点落在最新那个提交上。
- **没改文件的一轮没有检查点**，所以上下文领先于检查点是常态，不是异常。
- **中断的一轮也有检查点**：`completed=false` 只作记录，控制面选恢复目标时不看它，最新的检查点就算是中断的也会被用上。
  中断的提交本来就已经在工作分支上了，恢复后文件和上下文的差异由 Agent 自己察觉。

## 恢复：先文件，后上下文

控制面发现 Runtime 是空的（`/health` 的游标全 0），就按这个顺序把会话放回去：先恢复工作区，再注入上下文并播种 `seq`。

顺序不能反：先注入上下文的话，中间有一段窗口，Runtime 会接受一轮 run，而模型记得的文件还不在磁盘上。

文件和上下文**不要求对应同一时刻**：文件跟 Project 走，上下文总是注入最新归档的那一版，版本号对不上是常态，差异由 Agent
自己察觉。旧沙箱既已销毁，因为版本不等就拒绝恢复，只会让项目永久卡死。

### 工作区

`POST /workspace/restore` 把工作区放回会话最新的检查点，和 run 互斥；会话还没有检查点时跳过这一步，不动文件。三种成功结果：

- `already_there`：工作区已经在这个提交上。
- `superseded`：工作分支（本地或远端）已经走到这个提交**之后**，切到或保留较新的工作，**不回滚**。
- `restored`：工作区落后或分叉，移到这个提交上。

`superseded` 是有意为之：检查点记录的是**那个会话**把文件写到了哪，不是 Project 现在在哪。把工作区回滚到旧会话的检查点，
会删掉另一个会话的成果，这比「模型看到一些它不记得写过的文件」严重得多。

失败要明确：提交在远端找不到，或者分支历史分叉、不知道该选哪一边时，都显式报错，由控制面转成失败。**不会**静默地从一个
空工作区开始：那样模型会以为自己从没写过任何东西，然后把已有的文件重写一遍，而且要过几轮才看得出来。

### 上下文与 seq

- **冷启动必须播种 `seq`**：`PUT /context` 同时带上控制面已有的两个游标，新记录从它们之后继续。控制面把撞号当成重发，
  静默丢掉，所以漏播不会报错。游标要在注入时现取，不能用检查点里记的：那时这一轮的事件还没推完，取小了同样会撞号。
- **没有上下文也要播种**：日志先于上下文推送，第一轮跑到一半丢掉的 Runtime 会让控制面只有记录、没有任何一版上下文。
  这时用 `PUT /cursors`，只播种、不注入。两者都只接受空 Runtime。
- **`PUT /context` 失败会撤回播种**：游标先于上下文写盘，上下文没写上时回滚到请求之前，`/health` 仍报全 0，控制面可以
  原样重试。控制面把非 0 游标当成「Runtime 已有自己的历史」，不回滚的话它不会再注入上下文，这个会话就失忆了。
  进程在两次写盘之间退出时没有回滚，这个缺口仍在。
