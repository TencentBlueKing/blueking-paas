# 安全

Agent 运行模型写的代码，模型能读到的东西就要当成可能泄露的东西。本文只讲凭据保护的原则，具体实现以代码为准：
Shell 环境见 `agent.py`，用户应用环境见 `app_supervisor/app_spec.py`，脱敏见 `masking.py`。

## 原则

### 一、密钥不进模型能用的环境

这是真正的控制措施。模型的 Shell 和 `launch_app` 拉起的用户应用，环境里都剥掉 Agent 的全部配置和各家模型的密钥变量。

- **按前缀整段剥，不逐个登记**：剥掉 `APP_SPARK_AGENT_` 开头的一切，确实需要的（比如应用端口）再显式加回去。
  逐个登记的话，新增一个配置忘了登记就会漏进去，而且没有任何测试会因此失败。
- **凭据不进命令行**：同一个容器、同一个用户下的任何进程都能从 `/proc` 读到别人的 `argv`，一个 `ps` 就能抵消上面的隔离。
  要交给子进程的凭据走环境变量，也不落盘。Git token 的做法见 [harness_state.md](harness_state.md#凭据只在一个进程的环境里)。
- **会写进用户仓库或模型环境的配置不得带凭据**：比如包源地址，它会写进 `uv.lock`，也出现在模型的 Shell 环境里，所以启动时就拒绝带凭据的值。

### 二、出站文本脱敏，作为兜底

第一层会**静默失效**：新增一个密钥却忘了处理，或者 harness 升级改了剥离规则，测试全绿、功能正常，密钥却已经进了模型能读的环境。
第二层就是为了在那时发现它：在出站文本里把已配置的密钥值替换掉。

- **用在持久、可检索的出口**：落盘的 AG-UI 事件、HTTP 错误响应体、进程日志。这些是事后审计和排查会去翻的地方。
- **实时 SSE 不脱敏，是有意的**：逐个 delta 匹配要在每个 token 上跑，而它要防的值只有在第一层已经失效时才会出现；
  模型把密钥切成两段输出时它照样漏。落盘副本按消息合并后才脱敏，拿到的是完整字符串。客户端在自己的流里看到凭据，
  说明它本来就能拿到凭据。
- **匹配值，不匹配键名**：否则 `APP_SPARK_AGENT_MODEL_API_KEY` 这种名字在日志里就没法读了，也保护不了什么。
- **它是兜底，不是控制措施**：只认精确的配置值，重新编码、截断、拆分过的值一律穿过。不能靠它来放宽第一层。

### 三、沙箱里只放最小范围的凭据

沙箱里跑的是模型写的代码，所以注入的每个凭据都按「可能被读到」来设计范围：

- 模型网关用用户态的 access_token，不注入平台应用的 `bk_app_code` / `bk_app_secret`。
- 控制面 token 只授权这一个会话；Git token 只限这一个 Project 的仓库。
- 业务接口全部校验 Runtime token，不提供交互文档和 OpenAPI：沙箱放开公开流量后，换个端口就能打到这里，
  接口结构不该白送出去。

### 四、文档和示例只用占位符

README、docs、测试数据和提交记录里都不出现真实密钥，统一写 `replace-me` 这类占位符。
