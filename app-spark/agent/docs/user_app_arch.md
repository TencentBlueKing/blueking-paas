# 用户应用架构

Agent 在 workspace 里写的应用，怎么组织、怎么管依赖、怎么在沙箱里拉起来预览。部署到开发者中心不在本文范围，
但本文的平台配置就是为它准备的。

具体实现见 `app_spark_agent/app_arch/`（项目与平台配置）、`app_spark_agent/app_supervisor/`（拉起与监督）
和 `app_spark_agent/tools/`（模型工具），数值与约束以代码为准。

## 整体决策

- **应用形态固定**：一个 FastAPI 应用，从 `main.py` 导出为 `app`，用 uvicorn 启动。入口名同时写在提示词里，
  模型写成别的名字，预览和部署都会失败，所以两处必须一起改。
- **应用不选端口**：端口由启动命令决定。预览和部署共用同一份 uvicorn 参数，只有端口各自传入，避免两边漂移。
- **源码就是全部**：依赖文件和平台配置都在 workspace 里，随源码一起保存进 Git。换一个沙箱、换一个会话，
  拿到源码就能装好依赖、跑起来、部署出去。
- **模型决定时机，程序决定内容**：什么时候建项目、叫什么名字交给模型；模板、锁定的版本、平台配置由程序生成，
  不能指望模型照着抄对。
- **只在真要写代码时建项目**：run 开始时什么都不写，只聊天的一轮不会因为模板文件而多出一次提交。

## 项目依赖

依赖属于用户项目，不属于平台：`pyproject.toml` 和 `uv.lock` 在 workspace 根目录，环境建在 `<workspace>/.venv`。
平台只提供模板和包源。

- **建项目**：模型调 `init_project(name)`，按 `app-template/` 写出两个依赖文件和平台配置。
  - 「已有项目」只看 `pyproject.toml`，和 launch 判「还没有项目」用同一个条件，否则两边会把模型互相推给对方。
  - 有 `pyproject.toml` 就永不覆盖依赖文件；只剩一个 `uv.lock` 时 uv 用不了它，连它一起按模板重写。
  - 上一次只写成一半时重试即可补齐。
- **模板与提示词是一对**：提示词里写着新项目的起始包清单，模型以为有什么，模板里就得有什么。改模板依赖的步骤见
  `AGENTS.md`。
- **加依赖**：模型在 Shell 里 `uv add` / `uv remove`，用户提出就允许，不设白名单；不用 pip、不写 `requirements.txt`。
- **launch 前对齐**：每次 launch（含自动重拉）都 `uv sync` 一次，因为两次 launch 之间模型可能加了依赖。
  不加 `--frozen`：模型手改了 `pyproject.toml` 却没重新锁时，就地重锁比报错更直接，`uv.lock` 因此可能在 launch
  时被改写，随这一轮一起保存。
- **Agent 与项目的环境隔离**：Shell 和用户应用的 `PATH` 都去掉 Agent 自己的 venv。否则裸 `python -c "import fastapi"`
  会用 Agent 的包跑通，把「项目缺依赖」误判成能跑，`pip install` 还会改到 Agent 自己。
  - 用户应用按「激活了项目 venv」的样子跑，它按命令名调用的 `python` / console script 也落在项目环境里。
  - Shell 不放项目 `.venv/bin`：它要等建项目和第一次 sync 之后才存在，模型跑 Python 走 `uv run`。
- **不下载解释器**：沙箱里只用镜像自带的 Python。模型改了 `requires-python` 时宁可当场报错，也不卡在一次注定失败的下载上。
- **包源**：Shell 和 launch 用同一个包源，模型 `uv add` 解析到的就是 launch 装的。模板的锁文件是对着缺省包源锁的，
  见 [ref_settings.md](ref_settings.md#app_spark_agent_package_index_url)。
- **缓存预热**：镜像构建时对模板 `uv sync` 一次再删掉 `.venv`，只留 uv 缓存，新项目首次 sync 不必联网下载。

## 平台配置

`app_desc.yaml`（开发者中心的进程与服务声明）和 `.python-version`（运行时版本）是平台生成文件，随源码保存，模型不手写。

- **三个写入时机**：`init_project` 建项目时首次写入；模型可调无参数的 `sync_platform_config` 补齐缺失、覆盖过期；
  每次 launch 也会同步。
- **建项目和同步分开**：建项目是一次性的，要项目名，奠定依赖基线；同步可重复，不要项目名，也从不碰依赖文件。
- **launch 时排在 `uv sync` 之前**：`.python-version` 是 uv 选解释器的输入，残留的过期版本会让 `uv sync` 先失败，
  排在它后面就永远修不到。
- **同步失败则 launch 失败**：不能留下「预览能跑、却缺平台必需文件而不能部署」的项目。没有项目时不写。
- **部署端口是常量**：`app_desc.yaml` 用平台规范的部署端口，与预览端口无关。它随源码保存，按预览端口写的话，
  换个沙箱 launch 一次就会在 Git 里留下与用户改动无关的 diff。

## 拉起应用

这是在沙箱里把代码跑起来供预览，不是发布到 PaaS。

### 只由模型触发

唯一的触发路径是模型的 `launch_app` 工具，进程内直调监督器，不走 HTTP、不碰凭据。只有 Agent 第一时间知道代码
什么时候真的能跑。

- **不接受参数**：端口、入口、预览路径都是固定的。
- **工具随 Runtime 自己组装的 agent 挂上**：注入自带 agent 的调用方（嵌入、单测）要自己把它交进去，否则提示词让模型调一个不存在的工具。
- **失败不中断整轮**：原因交回模型，它可以读日志、改代码再拉一次。
- **单轮次数有上限**，按轮清零：否则「失败→改代码→再 launch」会一直烧 token，用尽后让模型把原因报给用户。
- **结果分四档**：`ok`、`starting`（进程活着但还答不出）、`failed`（进程没活下来）、`refused`（本轮次数用尽）。
  `starting` 单列一档，是为了不把模型推去改一份没有问题的代码。

### 不产出地址

`launch_app` 只回状态和端口。浏览器该访问哪个 origin 由控制面签发，沙箱不知道自己被外面怎么寻址，也不该知道。
给模型一个地址，它就会把那个地址当成真的报给用户。

### 控制面怎么知道

launch 成功（含自动重拉）落一条 `app.launched` 到 `ui_events`，控制面 drain 这条就知道应用起来了，不需要 Agent
反向回调控制面。这条事件只落盘，不插进进行中的 `/runs` SSE，所以和控制面是最终一致的。

### 活着和能服务分开

`dev_server_status` 是 `not_started` / `starting` / `ready` / `stopped`，照 kubernetes 的 liveness / readiness 分两档：
进程在但还答不出是 `starting`，进程没了才是 `stopped`。合成一个「健康」会让「慢启动」和「崩了」变成同一个答案，
而这两者一个该等、一个该重拉。

- **就绪只认本机端口答得了一个 HTTP 请求**，任何状态码都算：应用返回什么是它自己的事。只连 TCP 不够，
  端口 bind 上到真能处理请求之间那段窗口里，预览打开只会拿到空响应。
- **探针只在被问到时才发**（查状态、launch 等待期间），监督循环不发请求，否则应用日志会被探针刷满，
  而那正是模型读 traceback 的那份日志。
- **慢启动不算失败**：launch 等不到应答也不停进程，只回 `starting`。停掉一个正在预热的应用救不了它，
  只会把「慢」变成「永远起不来」。
- **自动重启只看进程死没死，不看就绪**。次数有上限，从上次手动 launch 起算，成功也不清零，避免起来又崩时无限重启；
  用尽就停在 `stopped`，等模型再 launch。

### 重复 launch 与冲突

- 进行中的 launch 再打一次：冲突，不排队。
- 端口被不是本监督器启动的进程占着：冲突，不杀、不发事件。
- 已有本监督器的进程：一律先停再拉，为的是加载新代码。先停再 sync 是有意的：反过来 uv 会原地改写旧进程正在用的
  `.venv`；sync 失败时旧版本也已下线，但模型 launch 本来就是为了看新代码。

### 生命周期

run 与 launch 互不取消，run 结束不杀应用；进程关停或空闲退出时停掉应用子进程。

### 网络与环境

- **听所有网卡**：预览要从沙箱外访问。e2b 里每个沙箱是独立网络，应用端口都一样，会话之间靠沙箱主机名和外面的反向代理分开；
  `local_process` 的多个 Runtime 共享一台机器，才各分一个应用端口。探针只连本机，和听哪个网卡是两件事。
- **剥掉 Agent 的配置**：子进程环境整段剥掉 `APP_SPARK_AGENT_` 前缀，只把应用端口加回去。剥前缀而不是逐个去掉已知密钥：
  新增一个配置忘了登记就会漏进应用，而应用是模型写的代码。
- **日志**：应用的 stdout/stderr 和 `uv sync` 的输出都追加到应用日志，模型用 `read_app_log` 读它。打开日志失败不阻止 launch：已在听的应用照样判为成功。
