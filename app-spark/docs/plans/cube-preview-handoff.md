# Cube 预览：两个集群怎么交接

这份说明只覆盖「换成 cube 沙箱之后，浏览器怎么打开预览」。现在的 `local_process` 反代是临时做法，不在这份的目标形态里。

## 现在为什么是反代

本机没有独立预览域名。用户应用听在 API 进程同一台机器上的一个端口，浏览器打不开那个端口。所以 `app-spark-api` 签发一个自己域名下的地址，登录和项目归属通过之后，再把页面字节转给那个端口。

换成 cube 之后，API 和 Agent 跑在不同集群。页面、图片、WebSocket 再从 API 集群转发，流量会打在控制面上。目标是这些字节只留在 Agent 集群。

## 目标形态

两个集群各干一件事。

- **API 集群**只有控制面。它分配并记下这个会话的预览主机名，并在用户第一次打开时做权限检查：平台登录，加上这个人能不能打开这个会话。
- **Agent 集群**里是沙箱，以及一个预览入口。入口按 `Host` 把连接交给对应的沙箱 Pod。应用仍听 `0.0.0.0` 上的约定端口。

每个会话一个主机名，例如 `https://c3.preview.example.com`。DNS 指到 Agent 集群的入口，不指到 API。这个域名和平台 API 不是同一个可注册域。

没有路径前缀。`/static`、应用自己的重定向、WebSocket 都按应用原来的方式工作。

`origin` 到这时才落库。它不再能从「当前这个 API 请求」推出来，而是创建沙箱时分好、记在会话上。

## 第一次打开时发生什么

1. 用户已经在平台登录。浏览器打开 `https://c3.preview.example.com/`，请求进 Agent 集群入口。
2. 入口发现这个主机名还没有有效的预览 Cookie，就 302 到 API 集群的授权地址，带上要授权的主机名。入口不把页面转给 API。
3. 浏览器带着平台登录 Cookie 访问 API。API 确认这个人能打开会话 `c3`。
4. API 不能给预览域种 Cookie。`api.example.com` 的 `Set-Cookie` 写不到 `preview.example.com`。API 只 302 回预览域名，query 里带一张一次性票据。
5. 浏览器跟着跳回 Agent 集群。入口确认票据有效、主机名就是 `c3`，然后由入口自己在预览域上种一张短时效 Cookie，再 302 到 `/`。票据用过即废。
6. 之后的 HTML、图片、WebSocket 带着这张 Cookie 进同一个入口。入口认为 Cookie 仍有效，就把连接交给对应的沙箱 Pod。API 集群不再出现。

Cookie 过期，或主机名对不上，就从第 2 步再来一遍。

## 入口怎么知道票据和 Cookie 是真的

这一点还没定。两种做法：

**本地验签。** API 用只有自己持有的私钥给票据签名，里面写主机名和过期时间。入口只拿公钥，在本地核对签名、主机名和过期时间，不回 API。预览 Cookie 是同一份内容，后续请求重复做这道本地核对。

代价是收不回来。用户中途被移出项目，入口要到过期才知道。有效期得短，过期后再回 API 做一次真正的权限检查。

**每次回 API 问一句。** 入口拿到 Cookie 就向 API 集群确认它是否还生效。可以立刻作废。每个预览请求都会打到 API，只是不再转发页面本身。若不缓存，图片和脚本仍会把 API 打满。

本地验签是为了「不回 API 也能判断真伪」补上的一种做法，不是已经定下来的方案。

## 入口不做什么

入口不查用户，也不查项目。权限判断只发生在 API 那一次。入口只决定「这张凭证是否仍有效，并且是不是给这个主机名的」。

预览域名上不再挂平台接口。应用代码跑在那个源上，平台接口若也在同一个可注册域，Cookie 仍可能被带到平台。

## 和本机的关系

`local_process` 没有第二个集群，也没有预览域名，所以现在仍由 API 进程自己反代。cube 上线时换的是「浏览器去哪个主机名、入口把连接交给谁」，不是再做一个集中式反代。
