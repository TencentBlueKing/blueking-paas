# Forgejo 与 Git 源码持久化开发计划

调查日期：2026-09-09。状态：待实施。

本计划分为 6 个开发阶段，以及一个后续发布阶段。每阶段都有独立验收结果，可以分别提交 PR。其中有三个**决策关卡**，过不去就不继续往下走：

- 完成第 2 阶段，确认 Forgejo 选型及仓库独立鉴权能力。
- 完成第 5 阶段，形成自动保存与一致恢复闭环。
- 完成第 6 阶段，再默认启用 Git 持久化（还需外部生产 Forgejo 就绪，见前置决策）。

目前已调查仓库代码、官方文档及 Forgejo 源码；尚未实际启动 Forgejo，也未验证真实服务链路。真实服务验证安排在前两个阶段。

## 调查结论和设计基线

- 建议固定 **Forgejo 15.0.7 LTS** 作为首版开发、CI 基线，同时锁定镜像摘要。调查时 15 LTS 支持期到 2027 年 7 月。实施时确认该分支的补丁更新情况。[官方版本列表](https://forgejo.org/releases/15.x/)
- 该版本支持通过 API 创建指定仓库范围的 token，Git HTTP 路径也执行仓库权限校验。创建参数包含 `repositories: [{"owner": "...", "name": "..."}]`。[Token 数据结构](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.7/modules/structs/user_app.go)、[Git HTTP 实现](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.7/routers/web/repo/githttp.go)
    - 已核对实现：`httpBase()` 在鉴权分支里调用 `CheckRepoScopedToken(ctx, repo, GetScopeLevelFromAccessMode(accessMode))`，而 `accessMode` 对 pull 取 Read、对 push 取 Write。所以仓库隔离和“只读 token 不能 push”都由服务端强制，不依赖客户端自律。
    - 指定仓库范围的 token 只允许 `read/write:repository` 与 `read/write:issue` 四种 scope。**Agent 手里的 token 因此无法签发新 token，也做不了仓库管理操作**（改可见性、加协作者、转移所有权均被禁）。这是隔离性上的有利性质，设计时可以依赖。
    - 注意反面：指定仓库范围的 token 对**所有公开仓库**仍有只读访问。因此“仓库必须保持 private”是一条安全不变量，不只是默认值。
- **创建和撤销 token 要求用户名/密码 Basic Auth**。API 侧需要保管专用服务账号的管理凭据，Agent 只获取仓库范围的 token。[认证路由](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.7/routers/api/v1/api.go)
- 当前 [Project 创建服务](../../app-spark-api/app_spark_api/core/projects/services.py) 只有数据库事务；远程建仓需要单独的可重试流程。现有 [Agent 镜像](../../agent/Dockerfile) 还没有安装 Git。
- 第一版采用 **一个 Project 一个私有仓库、一条工作分支、一个活跃写入者**。API 管仓库与授权，Agent 执行 Git，现有会话状态复制继续保留。

### 三条前置决策

**仓库 token 长期有效，加密入库。** Agent 用的仓库范围 token 按 Project 签发一次、长期有效，不随 Runtime 代次轮换。理由是以后可能接入其他 Git 后端，那些后端的凭据基本都是长期有效的；让第一版就依赖“按代次签发/撤销”会把设计绑死在 Forgejo 的能力上。撤销因此退化为**生命周期与应急操作**（项目删除、凭据泄露、仓库归档），不是每轮对话的常规路径。

这条决策的直接后果是密钥要静态保存，而本服务此前没有静态加密设施（只有 `django.core.signing` 给状态回写 token 做签名，签名不是加密；BkRepo 凭据是明文配置）。不必为此引入新依赖：直接依赖里已有的 `blue-krill` 提供 `blue_krill.models.fields.EncryptField`，是基于 `cryptography`/Fernet 的 Django 字段，`cryptography` 也已在 lock 文件中。**token 明文用 `EncryptField` 存，同时单独存 token ID 用于撤销。**

**旧写入者的防护改由 Git 服务端承担。** 因为凭据不再按代次失效，“撤销凭据”就不再是阻止一个跟丢的旧 Runtime 推送的手段。替代机制有两层，都必须落地：

- 服务端禁止非快进推送。一个被替换掉的旧 Runtime 手上的历史必然落后于工作分支，它的推送因此会被服务端拒绝，无需知道它是谁。这是主要防线。
- API 侧的写入者租约只负责拒绝非属主的检查点回写，不假装能阻止推送本身。

**生产环境的 Forgejo 由外部提供，时间待定。** 本计划第 1 阶段只交付本地开发与测试环境。生产实例的托管、数据库、备份、TLS、以及 15.x 在 2027-07 EOL 前的升级路径都不在本计划范围内，将由外部服务提供。**第 6 阶段的“默认启用”以该外部服务就绪为前置条件**，在此之前第 6 阶段的验收在开发环境完成，功能保持在开关后面。

本计划的持久化范围为**纳入 Git 管理的项目文件**。源码、配置、静态资源、依赖锁文件均可包含；`.venv`、`node_modules`、运行数据等是否保留由第 3 阶段的文件策略定稿（那里也给出体积上限）。若仍要求完整工作区恢复，这些文件需要补充快照或持久卷，不能宣称 Git 已覆盖全部文件。

## 第 1 阶段：增加 Forgejo Compose 和测试环境

建议在 `app-spark/repo-server/forgejo/` 放置 Compose、配置示例、初始化脚本及说明。线上 chart（MySQL 8 + PVC）后续再补。

### 开发内容

- 使用固定版本镜像，本地采用 SQLite 和持久化数据卷；生产数据库选型不绑死在开发配置里。
- 提供无需网页操作的初始化流程：创建初始管理员、专用服务账号、App-Spark 组织。
- 初始化可重复执行，保留已有仓库和凭据；生成的密码不进入版本库或普通日志。
- 明确宿主机 API、容器内 Agent 分别使用的访问地址，避免把 `localhost` 当成通用地址。
- 分开提供开发持久卷和测试临时卷；普通停止操作保留开发数据。
- 提供启动、就绪检查、初始化、日志查看和测试环境清理入口。[Forgejo Docker 配置说明](https://forgejo.org/docs/v15.0/admin/installation/docker/)

### 必须固化的服务端配置

这几项不是调优，而是安全与持久化的前提，要写进配置示例并在初始化脚本里校验：

- **工作分支开启分支保护，禁止非快进推送、禁止删除分支。** 检查点绑定 commit，历史一旦被强推覆盖，被覆盖的对象在 Forgejo 后续 GC 后就不可达，检查点随之失效——这会直接击穿第 5 阶段的恢复保证。同时这也是上面说的旧写入者主防线。
- **关闭 push-to-create**（`ENABLE_PUSH_CREATE_ORG`、`ENABLE_PUSH_CREATE_USER`）。否则仓库名写错会静默建出一个新仓库，而不是明确失败。
- **服务账号不能启用 2FA。** Forgejo 对启用了 2FA 的用户直接拒绝以用户名/密码做 Git over HTTP 操作，签发 token 的 Basic Auth 调用也会受影响。
- **仓库创建时即为 private，并确认没有任何路径能把它改成 public。**

### 验收

从空数据卷启动并完成初始化；重复初始化不产生重复账号；重启服务后测试仓库仍存在。宿主机和测试容器都能访问 Git 服务。上面四项服务端配置各有一条对应的验证：强推被拒、推送不存在的仓库名失败、服务账号能用 Basic Auth 完成 Git 操作、新建仓库确实是 private。

## 第 2 阶段：API 为每个 Project 建仓并分配独立凭据

建议新增 `repository/git/` 领域模块，单独管理 Git 仓库。现有 `SourceStorage` 面向文件包存取，不适合承载仓库、分支和凭据生命周期。

`ProjectSourceStorage` 的归属要一并交代清楚，否则仓库里会留下两套互相矛盾的答案：[app-spark-api README](../../app-spark-api/README.md) 目前把它写成冷启动恢复源码的**唯一**衔接点（“注入 context 之前先把源码 `get()` 回来”），而本计划改用 Git。它目前只有模型、迁移和测试，生产路径里没有调用者。**本阶段声明其冷恢复职责被 Git 取代，并同步改写 README 的“已知缺口”一段**；代码是删除还是留作导出用途，在本阶段的 PR 里明确给出结论。

### 开发内容

- 新增 Project 与仓库的一对一关联，记录远端仓库 ID、owner/name、默认分支及 `pending / ready / failed` 状态。
- 使用现有 HTTP 客户端依赖封装少量 Forgejo 接口，首版无需引入完整 SDK。
- Project 落库后，在事务外执行建仓；远程失败保留 Project 和失败状态，支持显式重试、补偿处理。
- 建仓使用确定性名称和幂等检查。远端已建成但响应丢失时，应确认并关联已有仓库。
- 签发仓库限定的读写 token，同时验证只读 token。token 长期有效，明文用 `blue_krill.models.fields.EncryptField` 加密入库，另存 token ID 供撤销使用。
- token 明文只返回一次；遇到响应丢失时，识别并撤销遗留 token，再重新签发。
- 撤销接口按生命周期与应急场景实现（项目删除、凭据泄露、仓库归档），不接入每轮对话的常规路径。
- 启动 Agent 前要求仓库处于 `ready`；已有 Project 提供显式补建入口。
- 记录 commit 用的 author/committer 身份，并定下它代表终端用户还是机器人账号。Git 在缺少 `user.name`/`user.email` 时直接拒绝提交，这不是可选项。

核心接口：

```text
POST /api/v1/orgs/{org}/repos
POST /api/v1/users/{service_account}/tokens
DELETE /api/v1/users/{service_account}/tokens/{id}
```

### 验收

必须使用真实 Forgejo：

- 通过 App-Spark API 创建 A、B 两个 Project，产生两个私有仓库。
- A 的凭据可以 clone/push A，不能读取或推送 B；B 同理。
- 只读 token 可以 clone，不能 push；撤销后新请求被拒绝。
- 匿名访问被拒绝。
- 加密入库的 token 取出后可用；数据库里存的是密文。
- 建仓超时、签发 token 响应丢失、重复及并发初始化均可恢复。

本阶段验收要跑真实 clone/push，所以 CI 环境需要 git 二进制，尽管给 Agent 镜像装 Git 是第 3 阶段的事。

这一阶段通过后，确认 Forgejo 的核心能力符合需求。

## 第 3 阶段：实现独立的 Git 工作区组件

先把 Git 操作做成确定性组件，再接入 Agent 执行流程。

### 开发内容

- Agent 镜像安装 Git 和 HTTPS 所需证书。
- 封装初始化、clone/fetch、检查工作区、提交、推送、按 commit 恢复等操作。
- 支持新增、修改、删除、重命名；无变化时不制造重复提交。
- 凭据仅在受控 Git 子进程中使用，不写进 remote URL、`.git/config` 或提交内容。
- 固定远端和目标分支；普通推送遇到分叉时明确报冲突。
- 为命令设置超时、非交互模式和可识别的错误类型。
- 明确文件策略，覆盖隐藏文件、二进制、符号链接和被忽略文件；已有工作目录导入时不覆盖原始内容。

文件策略必须在本阶段**定稿**，不能留作开放项——第 4 阶段的收尾延迟预算直接依赖它。首版给出默认忽略清单（至少排除 `.venv`、`node_modules` 一类可重建的依赖目录），并加一条硬性体积上限：超限时明确失败并报出是哪些路径，而不是安静地把一个几百 MB 的依赖目录推上去。

### 验收

临时仓库测试验证文件变化；真实 Forgejo 验证 push 后换一个空目录 clone，文件内容一致。另覆盖无变化、认证失败、分叉、超时和已有脏目录。

本地 Git 测试使用真实 Git 进程，不靠 mock 命令输出证明同步正确。

## 第 4 阶段：接入每轮 Agent 执行后的自动保存

接入当前 [run 收尾屏障](../../agent/app_spark_agent/server/routes.py) 中的 `_hold_run_stream()`。

### 屏障里只做本地 commit，push 交给后台

挂载点选对了，但**不能把 push 直接放进那个 `finally`**。有两个既有事实决定了这一点：

- 该 `finally` 在客户端断开时同样会走到，函数自己的注释就写明了"Reached on a client disconnect as well as on a completed turn"。
- SIGTERM 路径上 uvicorn 的优雅关闭超时只有 1 秒（`GRACEFUL_SHUTDOWN_TIMEOUT_SECONDS`），而且是**故意**用来掐断进行中的 SSE 的，`__main__.py` 的注释也写了"A cancelled run skips on_complete"。

两者叠起来意味着 Git 操作会有相当比例发生在**已被取消的 task** 里，那里每个 `await` 都可能立刻抛 `CancelledError`。在这种位置发起网络 push，无法保证它跑完——而“跑完才算保存”恰恰是本阶段要提供的保证。附带的第二个毛病是 push 是网络操作，放在这里会把流的关闭一起拖住，用户侧看起来就是这一轮卡住了。

正确的形状仓库里已经有了：现有的 `flush_replication()` 不是在屏障里做传输，它是**后台 replicator 之上的一道屏障**，传输失败不阻塞 run guard 释放，落后程度由 `/health` 的游标和 `replication_pending` 对外暴露。Git 保存照这个抄：

- **屏障内**：文件检查 + 本地 commit。纯本地、快、确定性强，即使在取消语义下也能完成。
- **屏障外**：push 由可持久化重试的后台任务完成，状态照 `replication_pending` 的样子暴露出去。

### 开发内容

- Agent 收尾逻辑自动执行文件检查与本地 commit，push 由后台任务完成；模型无需主动调用 Git。
- 正常完成、执行失败、客户端断开分别定义保存行为。失败产生的部分工作可以保存，但不能标成成功完成。
- 提交关联 `project_id / conversation_id / run_id`。
- 同步状态至少包含待保存、推送中、已保存、失败，以及本地和远端确认的 SHA。
- push 成功但 API 回写失败时，重试回写同一检查点，避免重复提交。
- 未完成同步时，第一版暂停接受下一轮，减少文件继续变化造成的复杂性。但**必须有逃生口**：网络分区下这条规则会把用户无限期挡住。给一个有界等待，超时后向用户暴露明确选择（继续但本轮不保存 / 继续等待），并说明由哪一层做拒绝、返回什么状态码——它会和 `RunGuard` 的 busy 判断叠在一起。
- 保留现有 SSE 行为，同时明确“模型执行结束”和“代码已远程保存”的区别。
- 暴露可观测信号，至少包括最老未保存提交的年龄和 push 失败计数。这是个持久化特性，“当前是否落后”必须能被直接查询，而不是只能从日志里推断。

### 验收

使用现有假模型驱动真实 Agent，执行一轮后从 Forgejo clone 能看到生成文件；断网时报告待同步，恢复网络后最终保存成功。

本阶段先作为受控开发功能，不允许依据旧的 `running=false` 就自动丢弃 Runtime。

## 第 5 阶段：实现工作区和上下文的一致冷恢复

扩展现有 [冷恢复入口](../../app-spark-api/app_spark_api/agent/conversations/services.py) 中的 `_resume_if_cold()`。

### 开发内容

- 引入可恢复检查点，关联仓库 commit SHA、会话上下文版本、日志游标、run 以及既有的 `state_epoch`。
- **检查点不能只存裸 SHA，要同时在远端固定一个不可移动的引用**（每个检查点一个 tag）。只记 SHA 的话，该 commit 一旦变成不可达对象，Forgejo 后续 GC 就会回收它，检查点随之失效——第 1 阶段的分支保护挡的是强推，挡不住“曾经存在后来被回收”。顺带一提，这和“后续阶段”里发布绑定不可移动标签是同一套机制，可以复用。
- 检查点对应的上下文必须保留独立版本。当前上下文 blob 会被覆盖，单纯增加版本号关联还不足以保证恢复。
- 上下文保留独立版本就要同时定下保留策略：只保留被有效检查点引用的版本，或保留最近 N 个，并给出回收路径。否则 blob 存储无上限增长。
- Git 提交已到远端、对应上下文已存储后，才把检查点标为可恢复。
- 新 Runtime 先恢复文件，再注入上下文和游标，最后接受新 run。
- 同一会话冷恢复使用配套检查点；会话切换继承 Project 最新有效代码，不能被旧会话检查点自动回滚。
- 本地有尚未推送的数据时保留并尝试恢复；远端不可用或 SHA 缺失时明确失败，不能悄悄启动空工作区。

### 验收

核心端到端场景：

> 第一轮生成文件 → 等待检查点成功 → 停止 Runtime，并移除测试用 workspace/state → 启动全新 Runtime → 文件与上下文同时恢复 → 第二轮继续修改原文件。

还要验证“代码已推送、上下文尚未保存”和相反顺序，均不会被误判为完整恢复点。

## 第 6 阶段：完善故障、回收和并发控制

这是默认启用前的必需阶段。注意本阶段的**验收在开发环境完成**，而“默认启用”还额外以外部提供的生产 Forgejo 服务就绪为前置条件，见前置决策。

### 开发内容

- 修正当前空闲退出直接 `os._exit()` 的路径，并协调现有退出超时，让 Git 保存有实际执行机会。
- 同步失败时阻止正常回收；强制销毁需要明确记录未保存状态。
- 将 Project 写入者所有权持久化，解决现有进程内 Runtime 列表无法覆盖多 API worker、API 重启的问题。
- 检查点回写校验写入者租约与既有 `state_epoch`，非属主的回写一律拒绝。**不要再引入一个平行的“Runtime 代次”计数器**——`state_epoch` 已经是这个概念，直接复用。
- 即使 Runtime 已消失，API 仍保留最后确认的保存状态，不能自动把“不知道是否保存”变成“保存成功”。
- 提供已有项目导入、失败任务修复、仓库备份恢复及配置文档。
- 把 Git 持久化的开关显式化，并支持按 Project 覆盖。第 4 阶段的行为会阻塞对话，出问题时必须能关掉而不必回滚部署。

### 关停顺序要和现有的吊销优先不变量对齐

原先设想的顺序是“阻止新 run、结束当前写入、保存检查点、撤销凭据、停止 Runtime”，这和现有 `terminate_runtime()` 的既定顺序冲突。[app-spark-api README](../../app-spark-api/README.md) 把理由写得很清楚：状态回写 token 是**先吊销再停进程**的，因为停进程是尽力而为（进程可能已经没了、可能不理信号、也可能本服务早就跟丢了），吊销 token 才是“不会再有东西以这个会话的名义写进来”的保证。

矛盾的根源是两种凭据性质不同，要分开写各自的不变量：

- **状态回写 token**：沿用现有 `state_epoch` 机制，先吊销，再停进程。这条不变量不许为了 Git 保存而放松。
- **Git 仓库 token**：按前置决策是长期有效的，关停时**不撤销**。因此它不参与关停顺序，旧写入者的防护完全落在服务端禁止非快进推送上（第 1 阶段配置）——一个被替换掉的旧 Runtime 历史必然落后，推送会被服务端拒绝。

据此，关停顺序为：阻止新 run → 结束当前写入 → 本地 commit 完成或明确标记为待保存 → 吊销状态回写 token → 停止 Runtime。注意这里等的是**本地 commit**，不是 push；push 由后台任务在 Runtime 之外继续重试，这也是第 4 阶段把 push 移出屏障带来的好处。

### 验收

覆盖空闲退出、主动关闭、断网重试、推送后进程崩溃、API 重启、两个 worker 同时启动同一 Project、旧 Runtime 延迟回写。强制崩溃的恢复上限明确为最后一个有效检查点。

其中必须有一个**旧写入者推送被拒**的用例：让一个历史落后的 Runtime 在被替换之后尝试 push，确认服务端以非快进为由拒绝、且工作分支未被改动。这是长期有效凭据下唯一的防线，不能只靠代码评审确认。

## 后续阶段：蓝鲸发布和额外 remote

在同步闭环稳定之后再推进：

- 为蓝鲸签发独立只读 token，将 Forgejo 作为外部 Git 源。
- 发布绑定固定 commit 或不可移动的发布标签；验证实际构建使用的版本。
- 自动保存与发布分别触发。
- 增加外部仓库时，单独记录同步目标、分支映射、已同步 SHA 和失败状态；外部同步失败不影响 Forgejo 已保存状态。
- 首版只做明确方向的同步，双向协作另行设计冲突流程。

## 各阶段统一的交付要求

每个 PR 同步更新 README、配置和接口说明，执行 lint、类型检查、相关测试及迁移检查；阶段合入前执行适用的完整检查。按照项目 AGENTS.md 指令，单元测试由子代理运行。

真实 Forgejo 测试应有独立入口和 CI 任务：开发者未启用该入口时可不运行，但 CI 任务缺少 Forgejo 必须失败，避免整组跳过却显示通过。

最终端到端测试沿用现有 `live_server + 真实 Agent + fake model`，串入真实 Forgejo，全程无需调用付费模型。
